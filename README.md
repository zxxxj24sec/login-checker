# login-checker 登录验证工具

携带账号密码发起登录请求，通过「登录前后内容差异」判断是否登录成功。

仅支持两种检测方式：

- **单条检测**：命令行直接给 `--url` / `-u` / `-p`，检测一个账号
- **文件批量检测**：`--file` 指向文本文件，一次性检测多个网站账号

## 用法

### 单条检测

```bash
python login_request.py --url <登录地址> -u <账号> -p <密码>
```

### 批量检测

准备一个文本文件（如 `accounts.txt`），每行一条 `url:username:password`：

```text
https://example.com/login:admin:123456
https://other-site.com/api/login:foo@bar.com:secret
http://192.168.1.10:8080/login:root:toor
```

然后：

```bash
python login_request.py --file accounts.txt
```

逐条实时输出 `成功 / 失败 / 异常`（边检测边打印进度），最后给一行汇总。**检测完成后会单独输出「成功清单」**，完整列出所有成功的 `url:username:password`（含密码）。

**成功结果会自动写入文档**：按根域名分组，每份文档以根域名命名（如 `ncepu.edu.cn.txt`），
内容为每行一条 `url:username:password`。同一根域名下的所有成功条目汇总到同一份文档。
默认写到脚本所在目录，可用 `--output-dir` 指定输出目录。

**格式错误的行会先单独列出并跳过**（含行号和原因），其余有效条目继续正常检测。文件若带 BOM（如 Windows 记事本保存的 UTF-8），脚本会自动识别处理。

退出码：`0` 全部成功，`1` 存在失败或异常，`2` 文件无有效条目。

批量检测默认以 **20 个并发** 同时检测，可用 `--concurrency N` 调整。

### 大批量（上千条）建议这样跑

```bash
python login_request.py --file accounts.txt \
    --timeout 3 --concurrency 32 --hard-timeout 15 --max-time 1800
```

- `--hard-timeout 15`：单条最多等 15 秒，超过就丢弃并记为"异常"，不再拖住整个批次
- `--max-time 1800`：整轮最多跑 30 分钟，到点立刻输出已完成的结果并退出（不会卡在最后几条）
- 运行中每 25 条会打印一行进度（含已用时间、预计剩余），输出实时刷新，重定向到文件也看得到进度

### 批量文件格式说明

- 每行一条 `url:username:password`，**冒号分隔**
- `#` 开头的行视为注释，空行自动忽略
- URL 必须 `http://` 或 `https://` 开头，**可带端口**（如 `:8080`）和 IP（如 `192.168.1.10:8080`）
- **用户名不能含冒号或斜杠，密码不能含冒号 `:`** —— 脚本会做校验，含冒号的行会被判定为「格式错误」并跳过（不会静默错位）
- **密码为空的行会直接跳过**。空密码登录成功几乎必然是误判——没有登录框的静态页
  POST 过去也会"原样返回"，容易被判成成功。跳过时会单独提示行号
- 格式错误 / 缺少用户名 / 空密码的行会被跳过，并在开头单独提示

### 常用参数

| 参数 | 说明 |
|------|------|
| `--file` | 批量检测文件，每行 `url:username:password` |
| `--url` | 登录接口地址（单条模式，http/https） |
| `-u` / `--username` | 账号（单条模式） |
| `-p` / `--password` | 密码（省略则交互输入，或读环境变量 `LOGIN_PASSWORD`） |
| `--user-field` | 用户名字段名，默认 `username` |
| `--pass-field` | 密码字段名，默认 `password` |
| `--json` | 以 JSON 格式提交（默认表单） |
| `--check-url` | 验证页地址，默认用登录页本身 |
| `--check-contains` | 验证页中应出现的内容（如 `"我的订单"`），出现即成功 |
| `--no-check` | 关闭行为验证，只看登录响应 |
| `--auto-fields` / `--no-auto-fields` | 自动从登录页抽取并携带隐藏字段（默认**开启**） |
| `-v` / `--verbose` | 打印详细诊断信息 |
| `--timeout` | 单次请求的超时秒数，默认 8 |
| `--read-timeout` | 读取单个响应体的总时间预算，默认 `timeout*2`（防慢速流） |
| `--hard-timeout` | 单条任务的硬超时，超时直接丢弃，默认 `(timeout+read-timeout)*2+5` |
| `--max-time` | 整轮批量检测的总时限，到点结束并输出已完成结果 |
| `--max-bytes` | 单个响应体最多读取的字节数，默认 512KB |
| `--dns-timeout` | DNS 解析超时，默认 3 秒（requests 的 timeout 不覆盖 DNS） |
| `--concurrency` | 批量检测并发数，默认 20 |
| `--progress-every` | 每完成多少条打印一行进度，默认 25（`0` 关闭） |
| `--proxy` | 显式指定代理，指定后不再读环境变量代理 |
| `--no-env-proxy` | 忽略 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量，全部直连 |
| `--output-dir` | 成功结果文档的输出目录，默认与脚本同目录 |

### 卡死防护

批量跑上千条时，"卡住"通常不是并发不够，而是下面几种情况。脚本已逐条设防：

| 现象 | 原因 | 对策 |
|------|------|------|
| 某条永远不返回 | 服务器每隔几秒喂一小块数据，requests 的 `timeout` 只管单次 recv，永远不触发 | `--read-timeout` 给"读完整个响应"设总预算 |
| 内存暴涨 / 读取极慢 | 站点返回几十 MB 的页面 | `--max-bytes` 默认截断到 512KB |
| 卡在 DNS | `requests` 的 timeout **不覆盖域名解析** | `--dns-timeout` 预解析，超时直接跳过（结果带缓存） |
| 最后几条拖很久 | 少数慢站点占满所有线程 | `--hard-timeout` 单条到点就丢弃 |
| 整体看不到头 | 没有进度反馈 | 实时 `flush` 输出 + 每 N 条打印进度与预计剩余；`--max-time` 可设总时限 |

另外，脚本启动时会打印一行 `网络：直连 / 经环境代理 ...`。如果你所在的终端注入了
`HTTP_PROXY`（很多 IDE/沙箱会），全部请求都会先进代理——想绕开就加 `--no-env-proxy`。

### 为什么会有大量「异常」

`异常` = 既没找到成功证据，也没找到失败证据，脚本按保守原则不判成功。常见原因：

- **需要验证码 / 短信 / 二次验证** —— 脚本无法自动完成
- **密码前端加密**（不少高校 CAS 会把密码 RSA 加密后再提交），明文密码必然被拒
- **需要登录页上的隐藏字段** —— 脚本默认已开启 `--auto-fields`，会自动带上 CAS 的
  `lt` / `execution` / `_eventId`、各类 CSRF token 等（用 `-v` 可以看到实际携带了哪些字段）

想提高准确率，最有效的办法是指定登录后页面的特征文字：

```bash
python login_request.py --url <登录地址> -u <账号> -p <密码> --check-contains "学号"
```

### 判定规则

判定按**优先级从高到低**，命中即出结果：

| 优先级 | 条件 | 结论 |
|--------|------|------|
| 0 | 页面要求验证码/二次验证（`验证码` / `滑块` / `短信验证码` / `captcha` / `recaptcha` …） | **验证码**（最高优先级，转入人工复核，单独输出、不进成功清单） |
| 1 | 显式 `--fail-contains` 命中 | 失败 |
| 2 | 接口明确返回认证失败（JSON 非 0 业务码 / `success=false` / HTTP 401·403·其他 4xx·5xx） | 失败 |
| 3 | 响应含登录失败特征词（`密码错误` / `认证失败` / `login failed` …） | 失败 |
| 4 | 显式 `--success-contains` 命中 | 成功 |
| 5 | 被重定向回登录页 / 脚本跳转到 CAS 统一认证页（`caslogin`/`authserver`/`passport`） | 失败 |
| 6 | 有强会话凭据 **且** 实质跳转到登录后页面 | 成功 |
| 7 | 有强会话凭据 **且** 脚本跳转（非静态、非 CAS） | 成功 |
| 8 | 有强会话凭据（`auth_token` / `access_token` / `login_token` / `jwt` …，凭据本身就是证据，不依赖跳转） | 成功 |
| 9 | 登录表单消失 **且** 出现登录后元素（`退出登录` / `我的账户` / `dashboard` …）<br>*须同时满足：匿名页确实有表单、且该元素匿名页没有；无基线则不启用* | 成功 |
| 10 | 响应内容仍是登录表单 | 失败 |
| 11 | 实质跳转到登录后页面（`/home` / `/dashboard` …） | 成功 |
| 12 | 兜底：登录前后页面内容相似度 ≤80%（变化明显） | 成功 |
| 13 | 兜底：登录前后内容相似度 >80%（内容未变） | **异常**（不武断判失败，避免漏掉正确密码，留待人工复核） |

其余（无任何明确证据）→ **异常**，保守不判成功。

> **关于相似度兜底的取舍**：脚本的定位是「宁可放过少量成功误报，也绝不漏掉正确密码」。
> 因此相似度低（内容变化明显）时判成功；但相似度高（内容几乎没变）时**不再判失败**，
> 而是退回「异常」留待人工复核——因为很多正确登录后的站点会返回几乎相同的页面
> （如 SPA 单页应用登录态由 JS 异步加载、或登录后停在骨架不变的确认页），
> 若据此判失败就会漏掉真实正确的密码。

**验证码/二次验证（优先级 0，最高）：**

页面一旦出现验证码、滑块、短信验证码、图形验证码等特征词，脚本会立即归入
「验证码」类别——这是**最高优先级**，先于所有成功/失败判定。因为：

- 需要验证码的站点脚本无法自动完成登录；
- 此时页面上出现的「登录后元素」「会话 Cookie」极可能是验证码页自带的干扰项，
  据此判成功必然误报。

验证码条目会：
- 在汇总里单独统计（`验证码 N`），实时输出时标签为 `验证码`；
- **单独写入 `<根域名>_captcha.txt`**，与成功文档 `<根域名>.txt` 分开，
  绝不与成功账密混在一起，供你后续人工复核。

**几点说明：**

- `成功` 优先认服务端行为证据（业务码 / 会话凭据 / 跳转目标）；页面文字只在
  "表单消失 + 出现登录后元素"同时成立时才作为成功依据。
- **「强会话凭据」≠ 通用会话 Cookie，且必须是「本次登录新签发」的**。三层收紧：
  1. `ASPSESSIONIDxxxx` / `ASP.NET_SessionId` / `JSESSIONID` / `PHPSESSID` / `sessionid` /
     `sid` 这类通用会话标识，**匿名访问就会下发**、登录失败时也下发，一律不算；
  2. 只有 `auth_token` / `access_token` / `login_token` / `jwt` 这类「登录后才签发」的凭据才算数；
  3. 匿名基线里**已经存在**的同名 Cookie，同样不算（很多站点匿名就下发 token 命名的
     Cookie，或非登录接口也返回 token 字段，纯靠名字判断必然误报）。
- 失败特征词 / 接口认证失败 **优先于** 页面特征：接口说失败，即使页面上碰巧
  出现"退出登录"，也判失败。
- 响应里的 `window.location` / `document.location` / `location.replace` 这类 JS 跳转
  **不单独作为成功证据**。两类假信号都会排除：
  - **站点固有静态跳转**：很多站点首页自带 `document.location='.../index.jsp'`，
    匿名访问就能拿到，与登录无关。脚本会用「匿名基线」对比——匿名时同样存在的
    跳转一律不算登录证据。
  - 无会话凭据时，即使跳转目标含 `index`/`home`/`main` 等词也不判成功，只判异常
    （`index.jsp` 这类名字太常见，纯靠名字判断必然误判）。
  只有**伴随会话凭据**时，JS 跳转才作为辅助证据。
- 「跳转」只认**实质跳转**：`http→https`、加/去 `www`、去默认端口这类 URL 规范化，
  不算登录导致的跳转，不会据此判成功。根路径 `/` 也不作为「登录后页面」证据
  （匿名访问就能到首页）。
- 「表单消失 + 出现登录后元素」同样要过**匿名基线**，否则极易误判：
  - 门户站 / 静态首页**压根没有登录框**，"表单消失"天然成立；
  - 首页静态链接里常带 `/dashboard`、`退出登录` 这类词（如 `?redirect=/dashboard`），
    匿名访问就能看到。

  因此要求：匿名页**确实有表单**（"消失"才成立）**且**该元素**匿名页没有**。
  拿不到匿名基线时该规则不启用，保守判异常。
- 想按页面文字精确判定，用 `--check-contains`（验证页应出现的文字）或
  `--success-contains`（登录响应应出现的文字）显式指定。注意：`--success-contains`
  **命中即成功，未命中不判定失败**，会继续按上面的规则往下判断。

退出码：

| 模式 | 退出码 |
|------|--------|
| 单条检测 | `0` 成功，`1` 失败，`2` 请求异常 |
| 批量检测 | `0` 全部成功，`1` 存在失败或异常，`2` 文件无有效条目 |

## 示例

```bash
# 单条：默认用登录页本身做前后对比
python login_request.py --url https://example.com/login -u admin -p 123456

# 单条：指定登录后才会出现的内容，判断更精确
python login_request.py --url https://example.com/login -u admin -p 123456 \
    --check-contains "我的订单"

# 单条：JSON 接口登录
python login_request.py --url https://example.com/api/login -u admin -p 123456 --json

# 批量：一次性检测 accounts.txt 里的所有账号（默认 5 并发）
python login_request.py --file accounts.txt

# 批量：调整并发数
python login_request.py --file accounts.txt --concurrency 10

# 批量：打印详细诊断
python login_request.py --file accounts.txt -v

# 批量：上千条，卡死防护全开（推荐）
python login_request.py --file accounts.txt --timeout 3 --concurrency 32 \
    --hard-timeout 15 --max-time 1800
```

## 说明

- 脚本零依赖：优先使用 `requests`，未安装时自动回退到标准库 `urllib`（两者行为一致）。
- 密码不会写入命令行历史：推荐省略 `-p` 走交互输入，或用环境变量 `LOGIN_PASSWORD`。
